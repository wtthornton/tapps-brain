# orchestration-prompt learnings (project-scoped)

Append one-line lessons as you generate prompts. Keep them project-scoped; never
bleed across repos. This file is created once by the scaffolder and never
overwritten on upgrade — it's yours.

<!-- - Validation goals need a verified-correct-negative Done-when, or the loop chases an unreachable target. (2026-06-18) -->

- Read the CI/config the loop will touch *before* drafting — for TAP-5459 that surfaced a hard blocker (`test_rls_spike.py` assumes a `tapps_runtime` role CI never creates) that would have failed the loop's first real run. A prompt written from the plan alone would have sent the runner into a diagnose cycle. (2026-08-03)
- This repo's `PreToolUse` sentinel on `save_issue` (30-min TTL, written by `docs_validate_linear_issue`) makes parallel Linear writes unsafe — agents race on a shared sentinel and a save can pair with another's validation. Bulk issue updates here are sequential-by-construction; say so explicitly or the runner defaults to a Workflow fan-out. (2026-08-03)
- Bake measured baselines into the prompt (suite counts, timings, non-default ports like `TAPPS_DEV_PORT=5442`). A cold session otherwise burns iterations rediscovering that `make brain-test` defaults to the wrong port. (2026-08-03)
- When the suite is slow (unit suite here is ~32 min at `-n 8`), state the *cadence* explicitly — full suite once per story at the pre-commit gate, story-only tests inside the edit loop. Without that the runner re-runs everything each iteration and pytest eats the budget. (2026-08-05)
- Enumerate the repo's multi-file "chain" requirements as their own prompt section (new endpoint → MCP tool + profile YAML + route map + three pinned-count tests + OpenAPI snapshot + docs). This repo's startup drift check turns a missed link into a boot failure, and a cold session finds those links one red CI at a time. (2026-08-05)
- Carry decisions the user already made into the prompt as "do not relitigate" lines. A prompt that leaves a settled design question open invites the runner to re-open it and burn an iteration re-deriving the answer. (2026-08-05)
- Corrected baseline: the unit suite runs **~16-20 min at `-n 4`**, not the 32 min quoted at `-n 8` — on a shared box `-n 8` mostly buys contention. Always pair the number with the flag, and add the rule it depends on: **freeze the working tree while a full suite runs.** Editing mid-run produced 39 failures + 116 errors describing neither the old tree nor the new one, and the run had to be redone. (2026-08-06)
- If a prompt covers more than one story that adds a migration, say up front that each story branches off the previous one. `postgres_migrations.py` rejects duplicate versions, so stories branched independently off `main` both claim the next number and collide on merge — the stacking is forced by the schema, not a style preference. (2026-08-06)
- A "known-failing quality scores — do not chase" list must name the **mode it was measured in**. `tapps_validate_changed(quick=true)` and full mode disagree badly (`kg_service.py` scored 66.2 quick / 73.9 full — fail vs pass), so a list measured in one mode sends the runner hunting a phantom regression in the other. (2026-08-06)
- Say that CI on the pushed commit is a *stronger* 0-failed proof than a local suite, and that re-running a full local suite on an already-green commit is waste. Two ~18-minute local runs were spent re-proving what a clean-checkout CI job had already proven. (2026-08-06)
- Warn that wall-clock-sensitive tests will misfire under the loop's own parallel suite. `test_import_time_under_200ms` failed 3 of 6 full runs purely from load; a prompt that lists such tests up front (or tells the runner to re-run a suspect standalone before diagnosing) saves a diagnose cycle per occurrence. (2026-08-06)
- For a **deploy/release** prompt, the Done-when is reachable only if the operator authorizes the irreversible steps — so it needs an explicit second terminal state: "operator declined, stop with a handoff naming what was declined." Without it, a decline reads as loop failure and the runner keeps retrying a merge it was told not to do. Same shape as the validate-goal correct-negative rule, applied to authorization rather than data. (2026-08-06)
- Mark **operator-only** steps as agent-inaccessible *and say the denial is expected*. `docker/.env` is hook-denied here (secrets), and it pins `BRAIN_VERSION`, which tags the locally-built compose images — so a runner that cannot edit it will ship 3.30.0 code under a `3.29.0` image tag and then diagnose a "failed deploy" that never happened. Name the file, the reason, and the visible symptom. (2026-08-06)
- Bake in known-benign failures with a *do not diagnose* label and a retry rule. `make dev-deploy`'s smoke step routinely fails with `ConnectionResetError` because it races the container restart; a fresh session treats that as a broken deploy and starts unwinding it. "Re-run once when healthy; treat a second failure as real" turns a 20-minute diagnose cycle into one command. (2026-08-06)
- When a prompt adds tools to an MCP profile, the chain is *seven* links, not one — and a prompt that says "five" is worse than one saying "several", because the runner stops looking after five. Measured on the 3.31.0 document-plane change: `mcp_profiles.yaml` + its header count comment + `tests/fixtures/profile_tool_sets/<profile>.txt` + `test_profile_registry.py`'s pinned count + `test_profile_filter.py`'s two + **`test_tool_filter.py`'s two more** (`test_bundled_coder_profile_returns_N_tools` and the `expected_counts` dict) + **any naming-rule assertion over the profile** (`startswith("brain_")` in both `test_profile_registry.py` and `test_profile_filter.py` had to widen to `("brain_", "document_")`). `ProfileRegistry.validate_against()` fails at **server startup**, so a missed link is a boot failure a test run never reaches — but the two `test_tool_filter.py` pins surfaced only in the *full* suite, not in the four files the prompt named as the sub-goal's proof. Equally important: say what is *already wired* — the document REST routes were mapped, and a runner "helpfully" editing `REST_ROUTE_TO_TOOL` would have introduced the drift it was avoiding. (2026-08-06)
- Don't let the prompt's own root-cause narrative become the fix's success criterion. The 3.31.0 prompt led with "the same-topic path bypasses the threshold", so the AND-gate read as *the* fix — but ablation showed the reported entries score 0.73–0.76 on the embedding path against a 0.7 threshold, so the gate passes them through and the **content-preservation floor** is what actually stops them. The prompt was right about the defect and wrong about which guard carries the case; the commit message inherited the error until a verifier caught it. A verifier that only re-runs the tests confirms both readings equally — only per-guard ablation ("revert A alone", then "keep ONLY A") separates them. Ask for that explicitly when a prompt ships more than one guard. (2026-08-06)
- Bake a *measured* green baseline with its exact command and count into Sub-goal 0 ("173 passed in 8.30s" for these four files). It doubles as a clean-tree check: a shared working tree with another session's edits shows up as a baseline mismatch before the first edit rather than as mystery failures later. (2026-08-06)
- When a fix narrows a matching rule, name the existing test that sits nearest the new boundary *and* say which way to resolve it. `test_finds_similar_entries` runs threshold=0.3 on tag-heavy overlap; without a "make the fixture more similar, never move the threshold" instruction, the cheapest path out of a red test is to weaken the fix it was written to prove. (2026-08-06)
